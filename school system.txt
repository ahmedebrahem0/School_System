# School System API - Frontend Guide

آخر تحديث: بعد تجربة Local SQL Server وMonster deployment.

هذا الملف مخصص للـ Frontend. الهدف منه يوضح المشروع، الرولات، الفلوهات، البرمشنز، والـ endpoints المهمة بدون دخول زائد في تفاصيل داخلية.

## 1. ملخص المشروع

School System API هو Backend لإدارة مدرسة. النظام يدعم:

- تسجيل ودخول المستخدمين باستخدام JWT.
- إدارة المستخدمين وتعيين الرولات.
- إدارة الطلاب والمدرسين والفصول والمواد والقاعات والحصص الزمنية.
- ربط المدرس بفصول ومواد.
- ربط الفصل بمواد.
- تسجيل الحضور والدرجات.
- عرض جدول الطالب أو المدرس حسب صلاحياته.

التقنيات الأساسية:

| الجزء | التقنية |
|---|---|
| Backend | ASP.NET Core 8 Web API |
| Database | SQL Server + Entity Framework Core |
| Auth | ASP.NET Identity + JWT Bearer |
| Mapping | AutoMapper |
| Docs/Test UI | Swagger |

## 2. البيئات

استخدم نفس الـ API contract في المحلي وفي Monster. الاختلاف فقط في الـ base URL والـ database connection.

| البيئة | Base URL | ملاحظات |
|---|---|---|
| Local | `http://localhost:5172` | يستخدم SQL Server المحلي `SQLEXPRESS` في Development |
| Monster | `http://schooolsystem.runasp.net` | يستخدم SQL Server الخاص بـ Monster |

ملاحظات مهمة:

- لا تستخدم `https` محليا لو السيرفر شغال `http` فقط.
- كل protected endpoint يحتاج header:

```http
Authorization: Bearer {token}
```

- `Content-Type` غالبا `application/json`، ما عدا إنشاء طالب من endpoint الطلاب يستخدم `multipart/form-data` لأن الأكشن عنده `[FromForm]`.

## 3. المعمارية

المشروع Clean Architecture بأربع طبقات:

| Layer | الدور |
|---|---|
| `SchoolSystemApi` | Controllers, Program.cs, Swagger, auth setup |
| `SchoolSystem.BusinessLogic` | DTOs, interfaces, services, mapping |
| `SchoolSystem.Domain` | Entities/models الأساسية |
| `SchoolSystem.Infrastructure` | DbContext, repositories, migrations, UnitOfWork |

قاعدة مهمة: الـ Frontend يتعامل فقط مع API DTOs، وليس entities الداخلية.

## 4. Authentication

### Register

`POST /api/Auth/Register`

Body:

```json
{
  "userName": "ahmed",
  "fullName": "Ahmed Ebrahem",
  "gender": "male",
  "email": "student@gmail.com",
  "password": "Student@123"
}
```

النتيجة: المستخدم يتسجل كـ user عادي بدون role. بعدها Admin يعين له role.

### Login

`POST /api/Auth/Login`

Body:

```json
{
  "userNameOrEmail": "admin@school.com",
  "password": "Admin@123!"
}
```

الـ response يرجع token وبيانات المستخدم. خزنه في الفرونت واستخدمه في `Authorization` header.

## 5. الرولات والفلو

### Admin

Admin هو صاحب التحكم الكامل.

فلو Admin المعتاد:

1. يعمل login.
2. يشوف users بدون role من `GET /api/Admin/users-without-role`.
3. يعين role لأي user من `POST /api/Admin/assign-role`.
4. ينشئ بيانات النظام الأساسية: subjects, classrooms, time slots, classes.
5. يربط class بالsubjects.
6. يربط teacher بالclasses والsubjects.
7. ينشئ timetable.
8. يدير students/teachers/grades/attendance حسب الحاجة.

صلاحيات Admin:

- يقرأ ويعدل ويحذف users.
- يعين ويشيل roles.
- يدير الطلاب والمدرسين والفصول والمواد والقاعات والحصص الزمنية.
- يدير العلاقات بين teacher/class/subject.
- يدير timetable.
- يدير attendance وgrades.

### Student

Student يشوف بياناته هو فقط.

فلو Student:

1. يعمل register.
2. ينتظر Admin يعين له role `Student`.
3. بعد login يقدر يشوف profile والدرجات والجدول والحضور الخاص به.

صلاحيات Student:

- `GET /api/Students/MyProfile`
- `GET /api/Grades/MyGrades`
- `GET /api/Timetables/MyTimetable`
- `GET /api/Students/attendance` بدون `studentName`
- يقدر يقرأ timetable class بتاعه فقط من endpoints المسموحة.

Student لا يقدر يعدل grades أو attendance أو users.

### Teacher

Teacher يشوف ويتعامل مع البيانات المرتبطة به فقط.

فلو Teacher:

1. يعمل register.
2. Admin يعين له role `Teacher`.
3. Admin يعمل teacher profile أو يربطه بكيان teacher.
4. Admin يربطه بفصول ومواد.
5. Teacher يقدر يشوف classes/subjects الخاصة به، ويسجل درجات وحضور ضمن نطاقه.

صلاحيات Teacher:

- يشوف `MyProfile`, `MyClasses`, `MySubjects`.
- يشوف classes والتفاصيل.
- يقرأ ويضيف ويعدل attendance للطلاب داخل الفصول المرتبط بها.
- يقرأ ويضيف ويعدل ويحذف grades داخل نطاق المواد والفصول المرتبط بها.
- يشوف timetable الخاص به أو المرتبط بفصوله/مواده.

Teacher لا يقدر يدير users أو roles أو reference data العامة.

## 6. ترتيب إنشاء البيانات الصحيح

هذا الترتيب يقلل أخطاء الـ 400/404/500 في التجربة:

1. Admin login.
2. Register user للطالب أو المدرس.
3. Admin assign role.
4. Admin ينشئ Subject.
5. Admin ينشئ Classroom.
6. Admin ينشئ TimeSlot.
7. Admin ينشئ Class.
8. Admin ينشئ/يحدث Student ويضع له `classId`.
9. Admin ينشئ/يحدث Teacher.
10. Admin يعمل ClassSubject.
11. Admin يعمل TeacherClass.
12. Admin يعمل TeacherSubject.
13. Admin ينشئ Timetable.
14. Teacher أو Admin يضيف Attendance/Grades.
15. Student يجرب MyProfile/MyGrades/MyTimetable.

لو `MyTimetable` رجع 400 للطالب، غالبا الطالب ليس مربوطا بـ class بعد.

## 9. قواعد مهمة للفرونت

- بعد register لا تعتبر المستخدم Student أو Teacher إلا بعد Admin assign role.
- لو endpoint رجع 401: غالبا token ناقص أو منتهي.
- لو رجع 403: token صحيح لكن role غير مسموح.
- لو Teacher حاول يعدل grade/attendance خارج فصوله أو مواده، المفروض يرجع منع صلاحية أو not found حسب الحالة.
- اعتمد على response DTOs، لأنها اتظبطت لتكون أنسب للفرونت بدل entity graph كبير.
- لا تعرض endpoints الخاصة بـ Admin في UI الطالب أو المدرس.
- اعمل guards في الفرونت حسب `roles` الراجعة من login.

## 11. تغييرات الحالة الحالية بعد الرينج

بعد التجربة العملية على Local وMonster حصلت تحديثات مهمة في الكود الحالي:

- `appsettings.Development.json` يستخدم SQL Server المحلي `SQLEXPRESS`.
- `appsettings.json` يستخدم Monster SQL Server production connection.
- تم منع `UseHttpsRedirection` في Development لتجنب Swagger/Postman `Failed to fetch` عند التشغيل المحلي على HTTP.
- تم إضافة CORS محلي يسمح بـ `localhost` و`127.0.0.1` في Development.
- تم إضافة `/health/database` لفحص اتصال قاعدة البيانات.
- تم تنظيف User Secrets المحلي من connection string الإنتاجي حتى المحلي لا يكتب على Monster بالغلط.
- تم إصلاح مشكلة EF execution strategy مع transactions في assign/remove role/delete user باستخدام `CreateExecutionStrategy()` داخل UnitOfWork.
- تم تحسين error response في auth/admin بحيث يظهر message واضح بدل 500 مبهم.

## 13. ملاحظات أمان ونشر

- لا تحفظ connection string أو JWT key في repo عام.
- الأفضل في الإنتاج استخدام environment variables من Monster بدل كتابة secrets داخل `appsettings.json`.
- بعد أي migration جديدة، نفذ database update على قاعدة Monster قبل publish لو فيه schema changes.
- بعد أي publish، اختبر:
  - `GET /`
  - `GET /health/database`
  - `POST /api/Auth/Login`
  - endpoint واحد من كل role.
